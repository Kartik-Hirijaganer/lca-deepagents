An MDA project is a folder of a few well-known files.

| File | What it does |
|---|---|
| `agent.py` | Defines the agent: its name, model, and tools |
| `instructions.md` | The agent's system prompt |
| `sandbox/__init__.py`, `sandbox/setup.sh` | Declares and provisions the sandbox the agent runs code in |
| `skills/` | Task-specific playbooks the agent pulls in on demand |
| `pyproject.toml`, `uv.lock` | Project dependencies |
| `.env` | API keys (LangSmith and your model provider) |

<details>
<summary>What MDA takes off your plate</summary>

| Self-hosted `deepagents` | Managed Deep Agents |
|---|---|
| You pick a sandbox provider, create a client, wire it in | `define_sandbox(scope="thread")`, one call |
| Prompt change → redeploy → restart → test | Edit `instructions.md` in **Context Hub**<br>(`instructions.md` = the system prompt)<br>live, with no redeploy |
| You stand up your own chat UI and logging | A chat UI and full tracing come for free |
| A real Slack integration means your own app, tokens, and webhook code | `channels.slack(...)`; MDA provisions the Slack app for you |

</details>

## `agent.py`: the agent itself

```python
from langchain.tools import tool
from managed_deepagents import define_deep_agent


@tool
def email_report(to: str, subject: str, body: str) -> str:
    """Email a report to a stakeholder. This simulates a send, no network call is made."""
    return f"Emailed {to}: {subject}"


agent = define_deep_agent(
    name="chinook-sales-assistant",
    model="anthropic:claude-sonnet-5",
    tools=[email_report],
)
```

Tools are unchanged from self-hosted deep agents; nothing about `email_report` is MDA-specific.

<details>
<summary>When would you split a tool into its own file?</summary>

`email_report` is a three-line helper, so it's fine right in `agent.py`. Once a tool needs its own dependency or setup, say an `internet_search` tool wrapping a Tavily client, it's cleaner to move it into its own file and import it:

```python
# tools/search.py
from langchain.tools import tool
from tavily import TavilyClient

@tool
def internet_search(query: str, max_results: int = 5) -> str:
    """Search the web for a query."""
    client = TavilyClient()
    return client.search(query, max_results=max_results)
```

```python
# agent.py
from tools.search import internet_search

agent = define_deep_agent(..., tools=[email_report, internet_search])
```

A `tools/` folder is one of MDA's opt-in pieces. It's worth doing once you have more than a couple of tools, or ones with heavier dependencies.

</details>

## `instructions.md`: the system prompt, edited live

`instructions.md` is this agent's system prompt: that it's Jane Peacock's Sales Support Agent, what database it has, what it should produce, how concise to be.

What's new is *where it lives*. Editing `instructions.md` in Context Hub takes effect immediately, on a deployment that's already running, with no redeploy needed. Add a persona:

```markdown
## Persona

Respond as a dramatic, woe-is-me Victorian-era child, mournful about every number
you uncover. Stay in character in every answer.
```

Save it, ask the same question again in the same chat, and the tone changes instantly. The SQL and the sandbox are unchanged; only the prompt is different. That's Context Hub in action, more on it below.

## `sandbox/`: where the agent's code runs

```python
# sandbox/__init__.py
from managed_deepagents import define_sandbox

sandbox = define_sandbox(scope="thread")
```

That's the whole sandbox declaration: no provider to pick, no client to wire up. `scope="thread"` gives each conversation its own sandbox, created on the first run and reused by follow-up turns, so later questions build on earlier work instead of recomputing it (until the thread ends or the sandbox's TTL expires). `sandbox/setup.sh` is what makes that sandbox ready, and MDA runs it once, before the sandbox's first use.

<details>
<summary>What sandbox/setup.sh actually does, line by line</summary>

```bash
pip install --quiet --break-system-packages pandas matplotlib
```

Installs the two libraries the agent's Python analysis relies on: `pandas` for querying and shaping data, `matplotlib` for charting (available, though this project's `instructions.md` tells the agent to stick to text).

```bash
curl -s -o /tmp/chinook.db https://raw.githubusercontent.com/lerocha/chinook-database/master/ChinookDatabase/DataSources/Chinook_Sqlite.sqlite
mv /tmp/chinook.db chinook.db
```

Downloads the Chinook sample database, the digital media store schema (artists, albums, tracks, invoices, customers) that Jane Peacock's team sells against, and puts it in place as `chinook.db`.

```bash
mkdir -p artifacts
```

Creates the `artifacts/` directory the sandbox writes generated files to, so the agent's first write to it doesn't fail on a missing folder.

Anything a real project needs installed or loaded before the agent can do useful work belongs here: extra Python packages, seed data, and credentials the sandbox needs to reach an internal service.

</details>

## `skills/`: playbooks the agent reaches for on demand

Skills work the same way they did in Module 3. In an MDA project they live in `skills/`:

```markdown
---
name: weekly-newsletter
description: Draft the weekly sales newsletter for Jane Peacock's team, covering top-selling tracks and artists, revenue by genre, and notable customer activity from the past week. Use whenever someone asks for the weekly newsletter or a weekly sales recap.
---

# Weekly newsletter

The weekly newsletter summarizes the past week's sales activity and breaks it down by genre and top artist...
```

Like `instructions.md`, a skill lives in Context Hub and updates with no redeploy.

**Context Hub** is where MDA stores a deployment's prompts and skills, separate from its code.

- Editing `instructions.md` or a skill there takes effect immediately, no redeploy needed.
- That splits code changes from behavior changes:
    - a new tool or a new model still needs `mda deploy .`
    - a prompt or skill edit doesn't need `mda deploy .` (since it never lived in the deployed graph to begin with)

<div class="callout" markdown="1">

`agent.py`, `instructions.md`, `sandbox/`, and `skills/` cover the core of an MDA project. A couple more pieces are opt-in: you add a file, MDA discovers it automatically at deploy time, and a new capability turns on.
</div>

## Identity: who's allowed to call the agent

```python
# identity.py
from managed_deepagents import define_identity, auth

identity = define_identity(auth=auth.langsmith_api_key())
```

`identity.py` declares who's allowed to call a deployment. It matters most once the agent needs to receive events from somewhere else, like Slack: an inbound message needs an identity to attribute it to, so `channels/` and `identity.py` go together in practice.

<details>
<summary>Other ways to authenticate callers</summary>

`auth.langsmith_api_key()` verifies a caller's LangSmith workspace API key; it's the simplest option, but everyone with the key shares the same threads. `auth.supabase()` is the other `auth.*` option on `define_identity`, for giving signed-in end users their own private threads. See the [identity docs](https://docs.langchain.com/langsmith/python/managed-deep-agents-identity) for details.

</details>

## Channels: putting the agent somewhere real

```python
# channels/slack.py
from managed_deepagents import channels

channel = channels.slack(
    name="chinook-sales-assistant",
    description="Answers questions about Chinook sales and drafts the weekly newsletter",
)
```

This is the same discovery pattern as `skills/`: a file that exports the right name, picked up automatically. MDA also provisions the Slack app itself as part of `mda deploy .`, so there's no app to create, no manifest to generate, and no token to copy in. Deploying walks you through authorizing the app for a workspace. After that, the agent can be DM'd or `@mentioned` from inside Slack, running on the same sandbox and skills as before.

<details>
<summary>Customizing how the Slack app looks</summary>

`name` and `description` are the two fields used above; `icon` is also available if you want the Slack app's avatar to match your own branding. All three are optional; they only affect how the app displays, never whether MDA provisions it.

</details>

Notice the shape repeats: a small file, a `define_*` or `channels.*` call, a module-level export, discovered by MDA without any registration step. `identity.py` and `channels/slack.py` use the same declarative pattern as `sandbox/` and `skills/`, applied to a new capability.

## Deploying it

One command builds and pushes a project like this to LangSmith:

```bash
mda deploy .
```

It prints an Agent Server URL to call and a LangSmith dashboard URL to inspect. The deploy loop is the same regardless of how many of these pieces a project uses.

<details>
<summary>What mda deploy . does under the hood, and common flags</summary>

It copies your project's files, generates a managed entry module, and writes a deployable build (including `langgraph.json`) to `.mda/build`, then uploads that build to LangSmith to run on the managed runtime. It reads `.env`, uses `LANGSMITH_API_KEY` for LangSmith, and forwards your model provider key as a deployment secret.

```bash
mda deploy . --name chinook-sales-assistant-dev --deployment-type dev  # custom deploy name and type
mda deploy . --workspace-id "$LANGSMITH_WORKSPACE_ID"             # target a specific workspace
mda deploy . --no-wait                                            # return immediately, don't wait for the build
```

(Each line above is a separate example; they're not meant to be combined.)

</details>

<details>
<summary>Other commands you'll reach for: logs, delete, evals</summary>

```bash
mda logs .                     # stream the deployed agent's server logs
mda logs . --lines 200 --level error
```

Streams new output until you press Ctrl-C in a terminal; piped or redirected, it prints the most recent lines (1000 by default) and exits.

```bash
mda delete .                   # remove the deployment and everything it created
```

Removes the deployment, its tracing project, the Context Hub repo holding this agent's context, and any managed sandboxes it created. Agent memory and thread history aren't recoverable afterward.

```bash
mda evals init                 # scaffold a Harbor eval workspace under evals/
```

MDA evals build on Harbor; `mda evals init` sets up the workspace, and `mda evals init -i` starts a coding agent to help write the eval tasks themselves.

Beyond `sandbox/` and `skills/`, an MDA project can also declare `tools/` and `middleware/`. Neither is used in this example project, but both are the same kind of opt-in, file-based declaration as everything else here.

</details>

## Recap

- `agent.py`, `instructions.md`, `sandbox/`, and `skills/` are the core pieces of any MDA project, and tools are unchanged from self-hosted deep agents.
- `instructions.md` and `skills/` both live in Context Hub and update with no redeploy; `agent.py` and `sandbox/` are code, so they still need `mda deploy .`.
- One sandbox per thread gives isolation and persistence automatically.
- `identity.py` (`define_identity(auth=...)`) declares who can call a deployment. It's optional on its own, required once a channel needs to attribute inbound messages.
- `channels/slack.py` puts the agent in Slack with no bring-your-own app; MDA provisions the Slack app itself and walks you through authorizing it on deploy.

- `"What were our top 5 genres by revenue?"`
- `"Which customers are in Jane's book of business?"`

```markdown
you uncover. Stay in character in every answer.
```

Save it, then ask the same question again **in the same chat**. The tone changes immediately, with no redeploy and no restart. The SQL and the sandbox are untouched; only the prompt moved.

## 6. Run the skill

Ask:

- `"Draft the weekly newsletter."`

That pulls in `skills/weekly-newsletter/SKILL.md` on demand, queries the database for the newest seven-day window, and saves the result to `artifacts/` in the sandbox. Edit the skill in Context Hub and re-run it to see the same no-redeploy loop apply to skills.


It prints an Agent Server URL to call and a LangSmith dashboard URL to inspect. With `channels/slack.py` in place, the deploy also walks you through authorizing the Slack app for a workspace; delete that file first if you'd rather skip Slack on a first deploy.

## 8. Tear it down

```bash
mda delete .
```

This removes the deployment, its tracing project, its Context Hub repo, and any sandboxes it created. Agent memory and thread history aren't recoverable afterward, so only run it when you're done.

## Definitions, not compiled agents

`create_deep_agent(...)` compiles an agent inside your own process, which is why it takes a `backend`, a `store`, and a `checkpointer`: you hand it the infrastructure it should use.

`define_deep_agent(...)` returns a definition instead. It's configuration, not a runnable agent. The `mda` CLI reads it on `mda dev` or `mda deploy .`, and the managed runtime compiles it and supplies those three pieces itself. That's why they disappear from the call signature rather than move somewhere else, and why the rest of the agent becomes the files above.

---

## What doesn't carry over

Tools, middleware, and subagents transfer as written. Four things don't:

| What | Why |
|---|---|
| A custom `BackendProtocol` | The runtime owns the backend. A managed sandbox is the only way to give the agent a filesystem and a shell. |
| Your own store or checkpointer | Threads, runs, and persistence come from Agent Server. Logic that depended on a specific store has to move into a tool or middleware. |
| Custom routes or surrounding app code | MDA hosts the agent, not a web app around it. Use a LangSmith deployment for that. |
| `state_schema` | `define_deep_agent` doesn't accept it in Python, so an agent extending `DeepAgentState` can't move as-is. TypeScript's `defineDeepAgent` does accept `stateSchema`. |

If none of those apply, the agent logic moves across unchanged; what you're rewriting is the wiring around it.
